## 0. 一句话

审核面板现在给玩家两把锤子（通过 / 打回）。但「打回」其实同时承担了两种完全不同的意思，
而其中占绝大多数的第二种，玩家手里根本没有对应的动作。

---

## 1. 问题：打回是一道悬崖

### 1.1 它是怎么发生的

AI 铸造出来的任务链是有顺序的：`chain.index` 递增，后一步默认吃前一步的产出。
玩家在「待议」栏上逐条裁决，每条只有两个按钮。

于是当某一步**太难**（或太枯燥）时，玩家只有一个动作可用：打回。
而打回是**从链里把这一步拿掉**。

拿掉之后会发生什么：

```
σ 第 2 步：把 Figure 3 的批次校正跑通          ← 玩家打回（"我一个本科生做不了这个"）
  第 3 步：把校正前后的差异写成一段可复现的说明  ← 还挂在链上
```

第 3 步没被删。它仍然在那里等一个已经不会出现的产出。
玩家点「通过」的那一刻，得到的是一件**站在半空中**的任务 ——
它的对象（校正后的数据）不存在，它的前置（第 2 步）被拿掉了。

这就是认知悬崖：**桥被拆了，对面那一步还在等你。**

### 1.2 更常见的其实是另一种

比"太难"更常见的是：**玩家根本没打算否定这一步的存在，只是不想要这个走法。**

> 「这一步太枯燥了，换个更轻量的做法。」

这句话里有两条信息：

| | 内容 |
|---|---|
| 否定的 | 走法（approach）—— 强度、形式、耗时 |
| 肯定的 | 存在与位置（intent & position）—— 它该在链上，它该在第 2 步 |

而「打回」把它读成了 **"这一步不该存在"**。

后果有三个，一个比一个贵：

1. **阶梯断了。** 见 1.1。
2. **AI 只收到否定，没收到方向。** `status: 'rejected'` 是一个负样本，
   但它说不出"往哪改"。下一次生成极可能给出一个同样强度、同样枯燥的东西 ——
   玩家再打回一次，然后放弃这条链。这不是 AI 不够聪明，是**信号里没有梯度**。
3. **玩家会开始骗自己。** 当唯一可用的动作是"删掉"时，人会选择点「通过」然后不做 ——
   于是面板上写着他接受了这一步，实际上他从没打算做。
   界面开始记录一个不存在的意愿。这是最坏的一种：**数据还在，但已经是假的了。**

### 1.3 为什么"整链重生成"救不了它

`ChainReview.regenerationCount` 已经有整链重生成（额度 1 次）。
但它回答的是另一个问题：

| | 整链重生成 | 换个平缓做法 |
|---|---|---|
| 玩家在说 | 「你**理解错**了我要做什么」 | 「你理解对了，但**这一步我迈不过去**」 |
| 颗粒度 | 整条链 | 一步 |
| 代价 | 极高（前面通过的全作废） | 低（其它步一个字不动） |
| 心理 | 重来一次 | 稍微改一下 |

用整链重生成去解决"某一步太难"，等于为了改一句话重写整篇文章 ——
而且额度只有一次，玩家会留给真的走错方向的时候，于是这一步他还是只能打回。

## 2. 形状：第三种裁决

裁决有三态，每种对应一个明确的语义：

| 动作 | 语义 | 对链的作用 |
|---|---|---|
| **通过** | 这一步成立 | 留在链上，`draft → offered` |
| **打回** | 这一步不该存在 | 从链中剔除，留痕作偏好信号 |
| **换个做法 ←新** | 这一步该在，但要换一种走法 | **原地替换**：旧版退场，新版顶上同一个链槽 |

**Reroute 不是打回的一个变体，是它的补集。** 打回是否定，reroute 是修正。
把它挂在打回下面（比如"打回 → 选原因"）会重复 1.2 的第三个后果：
玩家想修正的时候，被迫先做一个否定的动作。

### 2.1 玩家输入什么

一句话，自由文本，长度上限与 Spark Box 同级（200 字）。

```
这步太枯燥，换个更轻量的做法
我一个本科生做不了批次校正，有没有不用写代码的替代
不想读完整篇综述，能不能改成只读图
```

**不需要结构化选项。** "太难 / 太枯燥 / 太耗时 / 不相关"这种分类看起来更工程化，
但它会让玩家做两次表达：先选一个盒子，再把话塞进盒子里。
而且——最需要 reroute 的往往说不出属于哪一类。留一句话，让 AI 去分类。

### 2.2 AI 要收到什么（这一条是本设计的承重墙）

重写这一步，**最关键的输入不是这一步自己，是它的上下游。**

```
要换掉的一步        ：第 2 步 · 把 Figure 3 的批次校正跑通（难度 4）
它要喂给谁          ：第 3 步 · 把校正前后的差异写成一段可复现的说明  ← 必须一并给出
它吃谁的产出        ：第 1 步 · 把那篇论文的方法部分逐段读完
玩家的原话          ：这步太枯燥，换个更轻量的做法
约束                ：新版本的难度 ≤ 4；新版本必须仍然产出「一份可用于对比的数据」
```

漏掉"它要喂给谁"，AI 会写出一件孤立的好事 —— 难度确实降了，但第 3 步的对象没了，
悬崖只是从第 2 步挪到了第 3 步。

**所以 Phase 4 的 Reroute prompt 必须携带后继任务的 `objective` 原文。**
这是整个机制里唯一一处"少了就一定错"的字段。

### 2.3 约束（写进 prompt，也写进后置校验）

| 约束 | 理由 |
|---|---|
| 新难度 ≤ 旧难度 | 不设上限，"更轻量"可以更重 |
| 保留 `prerequisiteQuestIds`（上游不动） | 玩家否的是这一步，不是前面的路 |
| 必须声明产出仍能满足后继 | 见 2.2 |
| 奖励按新难度重算 | 见 2.4 |
| 一个字都不碰链上其它任务 | reroute 的代价必须真的低，否则玩家还是不敢用 |

### 2.4 奖励必须跟着难度重算

难度降了、奖励不变，reroute 就变成了一台刷钱机器：
把一个 5 星步骤换成 1 星，拿 5 星的钱。

奖励必须走**与生成时同一套** policy：`reward = f(难度, 职业线, 章节系数)`。
换句话说，reroute 不是"改一改文字"，是**一次完整的重新定价**。
这条如果 Phase 4 忘了做，玩家会发现，然后用它把经济打穿。

## 3. 契约形状（Phase 4 填空用）

### 3.1 为什么不是把 `ReviewQuestDraft` 的联合类型加一个成员

考虑过两种形状：

```ts
// 形状 A：加宽已有的联合
export type ReviewQuestDraft = (
  state: EarthOnlineState,
  questId: string,
  decision: 'approve' | 'reject' | 'reroute',
  now: Date,
  reroute?: { request: string },
) => EarthOnlineState;

// 形状 B：单独一个操作
export type RerouteQuestDraft = (
  state: EarthOnlineState,
  questId: string,
  request: string,
  now: Date,
) => EarthOnlineState;
```

**登记结论：走形状 B。制作人已批准（2026-10-07）。**

批准后的签名按制作人的原话定死在下面这一版 —— `ReviewQuestDraft` 一个字不改，
`RerouteQuestDraft` 是**专门给 AI 用的**那个（它的实现体内必然有一次模型调用）：

```ts
/** 原有契约，保持不动（原文照抄 types/state.ts:159） */
export type ReviewQuestDraft = (
  state: EarthOnlineState,
  questId: string,
  decision: 'approve' | 'reject',
  now: Date,
) => EarthOnlineState;

/** 新增：把一步换成一个更可行的走法（玩家给出修改诉求） */
export type RerouteQuestDraft = (
  state: EarthOnlineState,
  questId: string,
  request: string,             // 玩家原话，不做结构化 —— 结构化是模型的事
  now: Date,
) => EarthOnlineState;
```

理由不是审美，是这两类动作的性质不同：

- 通过 / 打回是**本地的**。玩家点头或摇头，状态立刻变，永远不会失败，永远不会等。
- 换个做法是**要等对方回话的**。它必然触发一次模型调用，可能超时、可能返回不合约束的
  结果、可能被重试。Phase 4 里它极有可能变成一个异步流程
  （界面挂 `ui.pendingAgentCalls` 的骨架屏）。

把"可能要异步"的动作塞进一个纯同步函数的可选参数里，会让 `ReviewQuestDraft`
从一个诚实的契约退化成一个什么都做的入口 —— 而它现在的价值恰恰在于**简单到不用想**。

形状 A 还有一个隐患：`decision` 是这一族的判别式，而 A 在它旁边挂了一个**只对某个取值有效**
的 `reroute` 参数。类型系统不会拦住在 `decision: 'reject'` 时传 `reroute` 的调用。

### 3.2 需要新增 / 扩张的字段

```ts
// Quest.origin —— 血缘
interface QuestOrigin {
  // ...现有字段不变
  /** 本任务是由哪一条任务 reroute 出来的；非 reroute 产物为 null */
  reroutedFrom: QuestId | null;
  /** 玩家每次要求换做法时的原话与结果，按时间追加 */
  rerouteHistory: RerouteRecord[];
}

interface RerouteRecord {
  at: ISODateTime;
  /** 玩家写的那句话 */
  request: string;
  /** 换之前那版的关键参数（难度 / 标题），用于在界面上给出"变了什么"的证据 */
  before: { title: string; difficulty: 1 | 2 | 3 | 4 | 5 };
  /** 换之后 */
  after: { title: string; difficulty: 1 | 2 | 3 | 4 | 5 };
  /** 若被后置校验拒绝（比如难度没降），记下原因而不是静默丢弃 */
  rejectedReason: string | null;
}
```

```ts
// ChainReview —— 额度与整链重生成分开计
interface ChainReview {
  playerNote: string | null;
  regenerationCount: number;      // 整链，上限 1（已有）
  rerouteCount: number;           // 逐次 reroute，上限 2（建议值，见 §5）
}
```

### 3.3 唯一一处会碰到冻结集的地方

`Quest.status` 是 Phase 1 冻结的联合类型。reroute 需要一个状态来表达
"这一版已经被换掉了，留档但不参与流转"：

- **建议**：新增 `'rerouted'`，与 `'rejected'` 并列。
- 复用 `'rejected'` 是不可接受的：两者的**信号价值相反**。
  `rejected` 说"这一步不该有"，`rerouted` 说"这一步该有，但换个走法"。
  未来的模型微调/偏好统计会把它们当成两件不同的事，合并等于烧掉最好的那批训练信号。

**这是本设计里唯一需要动 Phase 1 冻结集的一处**，也是它被推后到 Phase 4 的原因之一 ——
不该为了一个还没实现的机制，先动一次全局类型。

## 5. 刻意留白（留给制作人裁定）

这几件事**现在不定**，因为定了也是猜。写到 Phase 4 时带着真实用感再定：

1. **额度。** 每一步能换几次？建议 2 次。0 次等于没有这个功能；
   无限次会让"换个平缓做法"退化成抽卡 —— 玩家会一直换到抽出一张简单的。
   额度用完后，玩家仍可打回（那个动作是免费的、也是有限的：打回就是删掉）。

2. **旧版本留不留档。** 建议留，但折叠在"这一版之前的走法"里。
   理由：它回答的是「我是怎么走到这一步的」，那是成功日记同一类价值。
   代价是界面变长 —— 所以默认折叠。

3. **能不能一次性换整条链。** 建议不能。那是 `RegenerateQuestChain` 的事，
   两者的额度、代价、语义都不同，混起来会让玩家分不清自己在按哪个按钮。

4. **换完之后还能不能打回。** 建议能。reroute 不是单向门 ——
   换出来的版本仍然可以被否掉，只是这一次否决是**基于看过的具体方案**，
   而不是基于一个模糊的拒绝。这比现在好得多。

5. **要不要让玩家看见 AI 分类出的"类型"**（太难 / 太枯燥 / 不相关）。
   建议不显示在输入框旁边，但可以显示在结果里（"按'太枯燥'理解，给你换了一个…"）。
   让玩家能纠正它，而不是让它藏在暗处。

---

## 6. 一句话总结

**打回是把这一步从世界里删掉；换个做法是承认这一步该在，只是换一双鞋走过去。**

前者便宜、干脆，但它是一座桥被拆掉时最不该被给到的唯一工具。
